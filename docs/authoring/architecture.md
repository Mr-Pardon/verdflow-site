# 架构与扩展

<p class="lead">VerdFlow 的定位，是一套可跨工具复用的植被工作流。不同来源的区域、不同的种植方式与目标工具，通过共同的数据约定连接起来。</p>

目前可操作的完整路线以 DTS 为目标，包含实时选区、FBX 模型和 SHP / GeoJSON + 高程三种起点。跨工具复用是架构的设计方向，具体支持范围见下方[当前能力与后续方向](#当前能力与后续方向)。

## 先看懂一条种植流程

一次种植需要回答五个问题：**种在哪里、怎样分布、使用什么植被、落在多高的位置、交给哪个工具**。VerdFlow 把这些问题分别处理，再由同一个核心串联。

## 不同来源，先变成共同的区域

从 FBX 提取的绿地、从 GeoJSON 读取的面，以及在 DTS 中绘制的选区，原始格式和取得方式各不相同。进入种植流程前，它们都会整理成 **RegionSet（区域集）**，用一致的方式描述边界、孔洞和坐标。

策略因此只需面对“这是一块可以种植的区域”，不必分别实现 FBX 解析、SHP 读取和 DTS 绘制。

输入适配仍保留各自必要的步骤：FBX 需要检查模型并按材质提取区域，已有面数据则可以直接形成区域集。统一的是后续数据约定，不会强迫所有输入都经过材质分析。各路线能接收的几何也可能不同，详见[输入数据检查](../reference/data.md)。

## 空间组织与具体植被分开

**策略描述空间关系，植被搭配决定谁来承担这些关系。** 例如“主景”是一个角色，可以交给一种乔木，也可以由多种符合构图要求的植被按权重分配。

策略先生成带有角色的 **PointSet（点位集）**。点位描述位置、朝向等种植信息，不把某个 DTS 模型名写进空间算法。接着，植被搭配为点位选择具体资产，并解析本次使用的缩放等设置；分配结果与原始点位分开保存。

这让两种创作可以独立进行：设计者可以保留空间组织，替换植被；策略作者也可以改进算法，不必绑定某一套模型资源。跨目标平台时仍需准备该平台的资产绑定，不能把 DTS 模型名直接当作其他工具的资源。

资产库提供的是名称、目标资源定位、分类、缩略图与参考尺寸等信息，**不包含或安装三维模型**。角色的详细解释见[理解策略角色](./roles.md)。

## 界面、核心和适配器各管什么

可以把整体分工理解为三层：

| 部分 | 负责的事情 | 对使用者的意义 |
| --- | --- | --- |
| 操作入口 | Studio、实时 WebUI 和 CLI 接收选择与配置，展示状态和结果 | 可以为不同场景设计合适的交互 |
| 共用运行时 | Core 编排种植阶段，维护项目事实、任务与结果；宿主管理资源库和外部能力的生命周期 | 切换操作入口仍复用同一套业务规则 |
| 外部适配 | 处理文件格式、几何工具、高程来源和目标软件接口 | 新接入集中处理与外部工具的差异 |

界面通过明确的业务接口提交请求，不直接修改项目数据库，也不各自执行一套种植算法。耗时的策略计算、模型处理等工作交给受管理的执行进程，核心负责跟踪进度与取消等任务状态。

项目会保存输入、运行配置和结果之间的关联。一次运行固定策略包、参数、种子及本次搭配快照；固定区域、精确策略包、参数、种子和角色开关时，策略点位可复现。后续修改资源库，不会悄悄改写这次运行已经保存的输入。外部高程采样仍取决于实际地形数据与场景状态。

这里的项目持久化不等于实时面板能跨会话续跑。DTS 实时选区和连接仍有自己的会话边界，见[实时种植说明](../workflows/live.md)。

## 高程与输出，为什么也要独立

平面上的点位确定后，还需要知道它们落在地形上的高度。FBX 路线从模型几何采样，地理数据路线从 GeoTIFF 采样，实时路线向 DTS 场景查询。它们提供相同用途的高程结果，具体采样方式由各自适配器负责。

输出适配器再把点位、具体植被和高程组合成目标格式。当前 DTS 路线生成 XML，实时路线还会完成场景导入。**输出负责表达已有结果，不在写 XML 时重新生成空间分布。**

项目里的规范坐标保持不变，用户设置的 XML 坐标偏移只在最终输出时应用。因此可以调整偏移重新输出，也可以保留旧 XML，不必重新生成点位。输入数据的米制坐标对齐由用户在上游完成，当前不提供 CRS 重投影。

## 扩展一个能力，需要改哪里

| 想实现的变化 | 对应的扩展位置 |
| --- | --- |
| 新的群落关系、间距规则或空间分布 | 策略包：声明角色、参数与生成算法 |
| 新的植物资料、分类或目标模型名称 | 资产包：整理资源信息，再通过种植方案搭配 |
| 新的区域文件或区域取得方式 | 区域适配：产出约定的区域和坐标事实 |
| 新的地形或高程来源 | 高程适配：为标准点位返回采样结果 |
| 新的目标格式或场景工具 | 输出适配：解析该目标的资源绑定并交付结果 |
| 新的操作界面或自动化入口 | 应用接口：调用已有用例，复用任务与项目规则 |

例如，增加一种区域文件的读取能力，理想的改动范围是输入适配与必要的入口界面；策略仍消费区域集，后面的植被分配和输出继续复用。新增输出目标则重点处理目标资源和格式，不要求重写所有策略。

目前用户可以通过标准包扩展策略和资产。接入新的输入、高程、输出或客户端，仍属于开发工作，需要注册能力、验证坐标和结果契约，并补齐对应交互与测试。

<details class="details">
<summary>给开发者：Adapter、Provider 与 Worker 的区别</summary>

- **Adapter（适配器）**：外部能力的集成实现，处理某种格式、工具或协议。
- **Provider（能力提供者）**：供核心调用的一项明确能力，例如“形成区域”或“采样高程”。一个适配器可以提供多项能力。
- **Worker（执行进程）**：执行耗时工作的方式，由运行时管理进度、取消和进程清理。
- **Connector（连接器）**：管理外部应用的实时连接与回调，例如 DTS 会话；不负责种植算法。

这些分工服务于一条明确的种植主链。当前并不提供任意节点连接的通用工作流引擎，也没有可直接安装第三方适配器的插件界面。

</details>

## 当前能力与后续方向

| 当前可以使用 | 后续扩展方向 |
| --- | --- |
| Studio 项目工作台、DTS 实时面板；开发侧 CLI | MCP Bridge、Blender 客户端及其他操作入口 |
| FBX 提取、SHP / GeoJSON 区域、DTS 实时选区；配套的高程采样 | 更多区域来源、高程来源与区域约束处理 |
| 策略、资产与种植方案的标准包；VFS / VFA Author | 更完整的创作辅助与资源分享方式 |
| DTS XML 输出与实时场景写入 | 更多目标平台和输出格式 |
| 已验证的内置路线与专用交互面板 | 用户可安装适配器、受控的工作流组合与界面适配 |

Blender 当前已承担 FBX 几何处理与采样，但这不等于已经提供 Blender 内的完整种植客户端。后续方向按实际需求逐项验证，不代表当前客户端的可用功能或发布日期。

想先参与创作，可以从 [VFS Author](./strategy.md) 或 [VFA Author](./assets.md) 开始；想直接体验这条工作流，进入[选择你的上手路线](../guide/start.md)。
