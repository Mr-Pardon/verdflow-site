# 理解策略角色

<p class="lead">角色是一组点位在空间构图中的职责，而不是植物分类学中的一个名字。</p>

## 先谈关系，再谈树种

不要先告诉 Agent“我需要橡木角色、榆树角色和冬青角色”。先描述它们如何组织：谁形成主体？谁承接主体？谁沿边界分布？谁组成连续背景？

如果橡木与榆树使用相同的位置规则，只是外观不同，它们可以共同映射到“主景结构”一个角色，通过权重分配。如果榆树必须沿边界、橡木必须在中心，才需要考虑不同的角色或组织规则。

## 一个角色可以是什么

| 情况 | 是否需要独立角色 |
| --- | --- |
| 两种乔木共享同一空间规则，只想增加外观变化 | 通常不需要，使用同一角色的多个候选 |
| 草坪需要连续铺满，灌木只围绕主景形成组团 | 需要，因为位置职责不同 |
| 同一种植物一部分沿边界，另一部分形成中心主景 | 可能需要，物种相同不代表职责相同 |
| 只想让某植物更常出现 | 通常不需要，调整候选权重 |

角色可以设计为单候选，也可以允许多种植物按权重分配。关键是候选在当前策略的空间关系上可以互相替代，而不是要求整个产品只有一种固定的分配方式。

## 让 Agent 解释清楚

设计开始前，要求 Agent 为每个角色提供：

- 一个描述空间职责的名称，而不是先绑定物种。
- 它会出现在什么位置，与其他角色如何关联。
- 一至两个可替换的具体植被例子。
- 为什么不能简单地并入另一个角色。

然后让 Agent 用用户熟悉的场景重新说明。用户应能理解“换树种不一定要改算法”，而不必先学习技术字段。

## 一个简短的讨论示例

> 我希望低矮植被形成连续背景，较高植被集中在背景更密的地方。高植被可以随机使用橡木和榆树。

可以拆为“地表基质”和“主景结构”两个角色。橡木与榆树共享主景位置，不需要两个独立算法角色。

接下来才讨论背景覆盖、主景比例、两者间距与尺度。不应仅凭植物名称推导一整套生态关系。

## 保持角色数量克制

没有必要为每个视觉差异都新增角色。角色越多，用户要配置的候选、开关和参数越多，算法要验证的关系也越多。

从最小可解释组合开始。增加角色必须带来明确空间能力，而不是让清单看起来更丰富。

## 角色键与显示名称

显示名称方便用户理解，`role_key` 用于策略与搭配之间的匹配。两者都应稳定、明确。

改变职责或角色键时，认真考虑策略版本与已有搭配。不能仅把名称改了，就假定旧搭配仍表达同一关系。

## 角色开关的语义

禁用角色保证它不会进入最终点集，但其他角色是否重排，由策略自己定义。不要把“完整生成后过滤等价”作为所有策略必须满足的规则。

算法可以读取固定输入中的 `excluded_role_keys`，跳过关闭角色的专属计算，并明确规定剩余角色如何构图。只有作者承诺过滤等价时，才额外验证开关前后保留角色的逐点一致。

至少保留一个启用角色。作者应清楚说明某些角色关闭后，构图可能发生怎样的变化。

## 为用途补充示意与推荐

用途名称与职责来自策略的 `roles`。可在包内 `extensions.role_presentation` 补充用途分组、推荐素材、注意事项与静态构图示意，不需要为新策略改客户端。

示意使用有限的区域、乔木、灌木与地被符号，不接收自定义脚本、HTML、远程图片或任意 SVG。推荐只是说明，不改变候选校验、权重或生成规则；图示不是当前选区的实时结果。

声明必须覆盖所有角色，每个角色恰好归入一组。没有有效声明时回退到基本角色展示，不应阻断有效策略执行。具体格式和限制以当前 VFS Author 工具包为准。
